# Math review app for 7. klasse: design

Date: 2026-10-13
Status: draft, awaiting review

## 1. Purpose

A web app that helps a 7th grader in a Danish folkeskole review math. Its job is
to **find the gaps in what she knows and close them**: it works out which skills
she is weak in, drills those, and brings solid skills back at spaced intervals so
they stay solid. When she gets a problem wrong, an AI tutor (Claude) looks at her
actual answer, works out what she misunderstood, and explains it in Danish.

Her parent can follow her progress from their own device.

In the UI the app is called *Matematiktræning*; the name is one string and easy
to change.

### Success criteria

- She uses it a few times a week on her laptop.
- The number of skills marked *svag* goes down over the weeks.
- The parent can see that trend, and read her tutor conversations, from a phone.

### Users

Exactly two, with no sign-up:

- **The student**, who practises. On a laptop, with a keyboard.
- **The parent**, who reads progress and conversations. Mostly on a phone.

## 2. Scope

### In v1

- Math only, 7. klasse level, following Fælles Mål and the overlap of the common
  Alinea textbooks (Matematrix 7, Format 7, KonteXt+ 7).
- 24 skills (section 3), each with three difficulty levels, all generated by code.
- Typed answers with Danish number notation.
- Adaptive practice: placement round, per-skill strength and level, spaced review.
- AI tutor on wrong answers, with child-safety guardrails and a spending cap.
- Parent view: overview, skill map, tutor conversations, cost.
- Hosted on Fly.io in an EU region.

### Not in v1

- Other subjects. Nothing is built for them, though nothing in the design rules
  them out.
- Anything that needs drawing: constructions, sketching graphs, figures.
  Problems are text plus, where needed, a small table.
- Problems written by Claude.
- Points, streaks, badges or other gamification.
- More than one student; a settings page; offline use.
- Notifications to the parent (see section 13).

All UI text is Danish. Code identifiers and comments are English.

## 4. Problems and answers

### The problem shape

Every generator is `generate(level, rng) → Problem`, where `rng` is seeded. A
`Problem` has:

- `prompt`: Danish text, with math in `$…$` rendered by KaTeX (fractions shown
  stacked).
- `table` (optional): a small grid, for data lists and function tables.
- `answer`: the correct answer, as an exact value plus an answer kind (below).
- `inputHint`: one short line under the input box, e.g. *"Skriv svaret som en
  brøk, fx 3/4"*, *"Afrund til én decimal"*, *"Svar i cm²"*.
- `solution`: worked steps, in Danish, ending with the answer.

The seed and the full generated problem are stored with each attempt, so any
problem she saw can be shown again exactly, even after a generator changes.

### Answer kinds

| Kind | Accepts | Rejects |
|---|---|---|
| `number` | any equal value: `0,5`, `1/2`, `2/4` | |
| `decimal` | the value written as a decimal number: `0,25` | `1/4` when "som decimaltal" is asked for |
| `fraction-reduced` | the value in lowest terms, as a proper or improper fraction or a mixed number (`7/6`, `1 1/6`), or a whole number if it reduces to one | `2/4` when `1/2` is asked for; decimals |
| `percent` | `25`, `25 %`, `25%` | `0,25` |
| `rounded` | a value within one rounding unit of the exact value (e.g. ±0,1 when rounding to one decimal), or within 0,5 % of it, whichever is larger. This covers `3,14` versus `π`. | |
| `expression` | any linear expression in one variable with the same coefficients: `3 + 5x`, `5x+3` | |
| `solution` | `5` or `x = 5` | |

### Input rules

- Decimal comma: `2,5`. A period is also read as a decimal point (`2.5`).
- **Ambiguous input is not marked wrong.** `2.500` could be 2,5 or 2500, so the
  app asks *"Mener du 2,5 eller 2500? Brug komma til decimaler."* and the
  attempt doesn't count.
- Mixed numbers: `1 2/3`. Minus as `-` or `−`. Spaces are ignored except in
  mixed numbers.
- Trailing units are ignored: `cm`, `m`, `km`, `mm`, `cm²`, `m²`, `cm³`, `dm³`,
  `m³`, `L`, `l`, `kr`, `kr.`, `°`, `grader`.
- **Unreadable input is not marked wrong.** It gets *"Det forstod jeg ikke –
  skriv fx 3/4 eller 2,5"* and the attempt doesn't count.

## 5. How the app adapts

All of this is pure code with no database access, so it can be tested with
scripted histories. A skill's state is **replayed from its attempts in order**,
never edited in place. Changing a rule later means re-running the replay over
her stored history; nothing is lost.

### Per-skill state

- **Strength:** the weighted average of correctness over the last 8 attempts.
  The newest attempt has weight 1 and each older one ×0,8.
- **Level (1–3):**
  - The first attempt is at level 2.
  - Afterwards the level is 2 if that first attempt was right, 1 if it was wrong.
  - Three right in a row at the current level moves up one level (max 3).
  - Two wrong in a row at the current level moves down one level (min 1).
  - A level change resets the run.
- **Review schedule:** an interval index into `[1, 3, 7, 21]` days and a next
  review date. It only means something while the skill is *sikker*:
  - Becoming *sikker*: index 0, next review in 1 day.
  - A right answer while the review is due: index + 1 (stops at 21 days), next
    review that many days from now.
  - A right answer before it's due: no change.
  - A wrong answer: index back to 0.

### Status

The rules are applied in this order:

1. No attempts: **ikke prøvet**.
2. Fewer than 3 attempts: **svag** if the latest was wrong, otherwise **på vej**.
3. 3 or more attempts:
   - strength < 60 %: **svag**
   - strength ≥ 85 % and level 3: **sikker**
   - anything else: **på vej**
4. A sikker skill whose next review date has passed is shown as **skal
   genopfriskes**. This is computed when read, not stored.

### Placement round (kortlægning)

- Until every skill has been tried, the home screen offers *"Fortsæt
  kortlægning"*.
- A placement session is up to 12 untried skills, one level-2 problem each,
  ordered so topics alternate. Two sittings cover all 24.
- She sees right or wrong and the correct answer. There is no tutor and no retry,
  so it stays short. The gaps get worked on in normal sessions.

### Normal session

A session is **10 picked problems**, roughly 10–15 minutes. Retries (below) come
on top. Each answer is saved on submit, so she can stop at any point.

To pick the next problem:

1. Three pools:
   - **train**: skills that are svag or på vej
   - **review**: skills that are skal genopfriskes
   - **new**: skills that are ikke prøvet
2. Draw a pool with weights 60 / 25 / 15. Empty pools are skipped and the
   weights renormalised.
3. Within the pool:
   - **train**: pick at random among the 3 weakest.
   - **review**: pick the most overdue.
   - **new**: pick in curriculum order, alternating topics.
4. Never the same skill more than twice in a row (retries count).
5. If every pool is empty because everything is sikker and nothing is due, pick
   the skill with the earliest next review date. Answering it early doesn't
   advance its interval.

The picker takes `rng` as a parameter so tests are deterministic.

### After a wrong answer (normal session and Øv selv)

1. The attempt counts as wrong.
2. She sees the correct answer, with *"Hvorfor?"* (opens the tutor) and *"Prøv
   en lignende"*.
3. *"Prøv en lignende"* always comes next: a fresh problem of the same skill, at
   the skill's level after this attempt. It counts normally.
4. At most one retry per original problem. If the retry is wrong too, she sees
   the correct answer with *"Hvorfor?"* and *"Næste"*, and the session moves
   on.

### Øv selv

She picks any skill and gets 10 problems of it. Levels adapt as usual and the
attempts count normally.

### What she sees

- **Home:**
  - *"Start træning"*, or *"Fortsæt kortlægning"* while the placement round is
    unfinished
  - *"Øv selv"*
  - *"Mit kort"*
  - days practised this week (weeks start on Monday)
- **Mit kort:** all skills grouped by topic, coloured by status.
- **End of session:** a short summary, e.g. *"3 færdigheder blev stærkere i
  dag"*, which counts the skills whose strength rose during the session.

## 6. The tutor

### Trigger and flow

- After a wrong answer in a normal or Øv selv session she can press *"Hvorfor?"*.
  That opens a chat panel tied to that attempt.
- Claude's first message explains what probably went wrong. She can then send up
  to **6 messages** of at most 500 characters each.
- Pressing *"Prøv en lignende"* or *"Næste"* closes the conversation for good.
  The tutor never sees the next problem.
- Replies stream in.
- The panel says plainly: *"Dine samtaler med tutoren kan ses af dine
  forældre."*

### What Claude gets

- The problem text, skill and level.
- **The correct answer and the generator's worked solution**, marked as correct
  and not to be contradicted. Claude explains the reasoning behind the solution;
  it does not compute answers itself.
- Her answer to this problem.
- Up to 3 of her earlier wrong answers on the same skill (problem, her answer,
  correct answer), so it can spot a pattern.
- Not her name. It addresses her as *du*.

### System prompt rules

- Reply in Danish, warmly and simply, for a 13-year-old. Around 100 words per
  reply.
- Start from the likely misunderstanding behind *her* answer, then show the
  method using this problem's numbers.
- Stay on math and the current topic. Steer other subjects back politely.
- Explain methods. Don't hand out answers to other problems; guide instead.
- Never ask for personal information. No links.
- If she writes something that suggests distress or a safety concern: respond
  kindly, suggest she talks to a trusted adult, and call `flag_for_parent`.

### Flagging

- `flag_for_parent({ reason })` is a tool Claude can call.
- The server stores the flag and reason, returns `ok`, and the reply continues.
- Flagged conversations sort first in the parent view.

### Model and cost

| Config | Default |
|---|---|
| `TUTOR_MODEL` | `claude-sonnet-5-5` |
| Max tokens per reply | 1024 (see section 15) |
| `TUTOR_MONTHLY_CAP_USD` | 10 |
| `TUTOR_PRICE_INPUT_PER_MTOK` | 2 |
| `TUTOR_PRICE_OUTPUT_PER_MTOK` | 10 |

- Prompt caching covers the tools, the system prompt and the conversation so far.
- Each assistant message stores its usage: input, output, cache-write and
  cache-read tokens.
- Monthly spend is computed from that usage and the configured prices. Cache
  writes are priced at 1,25× input and cache reads at 0,1× input. The month
  follows Europe/Copenhagen time.
- Before each call, if this month's spend has reached the cap, the tutor is
  unavailable.
- A spend limit should also be set in the Anthropic console, as a second net.

### Fallback

If the tutor is unavailable (cap reached, API error, missing key), *"Hvorfor?"*
shows the generator's worked solution instead, with no error shown to her beyond
*"Her er løsningen trin for trin"*.

## 7. Parent view

Route `/foraelder`; `/forælder` redirects there. Built for a phone screen. It is
read-only, and the parent role can't practise, so her data stays hers.

1. **Overview**
   - last practised
   - days practised and minutes this week
   - count of skills per status
   - **trend of the number of svag skills per day**, computed by replaying
     attempts up to the end of each day
2. **Skill map**
   - the same map she sees, plus strength, level and last practised per skill
   - tap a skill to see its recent attempts, including exactly what she typed on
     wrong ones
3. **Tutor conversations**
   - flagged first, then newest first
   - each shows the problem, her answer and the whole chat
4. **Cost:** tutor spend this month against the cap.

Minutes practised are the sum of the gaps between consecutive answers in a
session, each gap capped at 5 minutes.

## 8. Logins

- One login page; the password decides the role. Two passwords live in config:
  `STUDENT_PASSWORD` and `PARENT_PASSWORD`. They are compared in constant time.
- The session cookie is signed with `SESSION_SECRET`, `httpOnly`, `secure` and
  `sameSite=lax`. It lasts 365 days for the student and 90 days for the parent.
- At most 5 failed logins per IP per 15 minutes, tracked in memory. That's fine
  on a single machine.
- Student routes reject the parent role and vice versa. Every API route checks
  the role.

## 9. Data

A single SQLite file at `DATABASE_PATH`, with plain SQL migrations.

| Table | Columns | Notes |
|---|---|---|
| `sessions` | `id`, `kind` (`placement` / `adaptive` / `practice`), `skill_id` (practice only), `started_at`, `ended_at` | |
| `attempts` | `id`, `session_id`, `skill_id`, `level`, `seed`, `problem_json`, `given_answer`, `correct`, `is_retry`, `created_at` | **Source of truth.** Unreadable or ambiguous input is not stored. |
| `skill_state` | `skill_id`, `strength`, `level`, `status`, `interval_index`, `next_review_at`, `attempt_count`, `last_attempt_at` | Cache, rebuilt from `attempts` after each answer for that skill. A script rebuilds all skills. `status` never holds *skal genopfriskes*; that is computed when read. |
| `tutor_conversations` | `id`, `attempt_id`, `flagged`, `flag_reason`, `created_at`, `closed_at` | |
| `tutor_messages` | `id`, `conversation_id`, `role`, `content`, `input_tokens`, `output_tokens`, `cache_write_tokens`, `cache_read_tokens`, `created_at` | |

**Privacy:**
- No name, email or other personal details are stored.
- Her name is never sent to Claude.
- Hosted in an EU region.
- Anthropic doesn't train on API data by default.

## 10. Architecture

TypeScript throughout, on Node 24 LTS.

| Part | Choice |
|---|---|
| App | SvelteKit with `adapter-node`: pages, server routes and API in one process |
| Database | `better-sqlite3` |
| Math display | KaTeX |
| Tutor | the official Anthropic TypeScript SDK, streaming to the browser over server-sent events |
| Fractions and parsing | our own small exact-fraction type and answer parser, no math library |
| Tests | Vitest for units, Playwright for one smoke test |

### Code layout (under `src/lib/` unless noted)

| Unit | What it does | Depends on |
|---|---|---|
| `math/fraction.ts` | exact rational arithmetic | nothing |
| `math/parse.ts` | Danish input → value, expression, or a reason it's unreadable or ambiguous | `fraction` |
| `math/check.ts` | `(answer, input) → right / wrong / unreadable / ambiguous` | `parse` |
| `skills/<id>.ts` | one generator per skill | `math`, a seeded `rng` |
| `skills/registry.ts` | skill id → generator | `skills/*` |
| `skills/curriculum.ts` | topics, skill order and Danish names | nothing |
| `adaptive/state.ts` | `replay(attempts) → SkillState` | nothing |
| `adaptive/pick.ts` | `pickNext(states, recent, now, rng)` and placement order | `state`, `curriculum` |
| `server/db.ts` | queries and migrations | `better-sqlite3` |
| `server/tutor.ts` | prompt building, API call, flag tool, spend check, fallback | SDK, `db` |
| `server/auth.ts` | login, cookies, rate limit | nothing |
| `src/routes/` | student pages (`/`, `/traen`, `/kort`, `/oev`), `/login`, `/foraelder/*`, and API endpoints for submitting an answer and streaming the tutor | all of the above |

`math`, `skills` and `adaptive` never touch the database or the network.

## 12. Errors

| Situation | Behaviour |
|---|---|
| Unreadable answer | message with examples; not counted |
| Ambiguous answer (`2.500`) | asks what she meant; not counted |
| Connection drops mid-session | nothing lost; each answer was saved on submit; the next visit starts a new session |
| Tutor unavailable | worked solution instead (section 6) |
| Generator throws | log it, pick a different skill; tests should make this unreachable |
| Wrong role or no cookie | redirect to `/login` |

## 13. Testing

Written test-first.

- **Parser and checker:** table-driven, covering every answer kind and input rule
  in section 4: `2,5`, `2.5`, `2.500`, `1 2/3`, `−3`, `25 %`, `3+5x`,
  `x = 5`, `48 cm²`, garbage.
- **Generators:** for every skill and level, 500 seeds. For each:
  - the generator's own answer is accepted by the checker
  - the solution's last step matches the answer
  - the answer meets the skill's "nice numbers" constraints (e.g. whole-number
    solutions to level 1 equations, no repeating decimals unless rounding is
    asked for)
  - the prompt contains no unfilled template markers
- **Proofreading:** `npm run examples` writes 3 examples per skill and level to a
  Markdown file, so the parent can proofread the Danish.
- **Adaptive engine:** scripted attempt histories, checked against the expected
  strength, level, status, review dates and picks, including the placement
  rules, the two-in-a-row limit and the empty-pool fallback.
- **Tutor:**
  - prompt building is unit-tested
  - the API is mocked: streaming, the flag tool, spend cap and fallback
  - `npm run tutor-eval` runs about 10 typical mistakes (e.g. adding numerators
    and denominators, sign errors, percent of the wrong base) through the real
    model and prints the replies for a person to read. It is not part of CI.
- **Auth:** role checks on every route group; rate limit.
- **Smoke test (Playwright, tutor mocked):**
  1. log in as student
  2. answer one right and one wrong
  3. open the tutor
  4. log in as parent
  5. see the attempt and the conversation

## 15. Changes made while planning (2026-10-13)

Found while writing and checking the implementation plan
(`docs/superpowers/plans/2026-10-13-math-review.md`):

- **Tutor reply limit is 1024 tokens, not 400.** Sonnet 5.5 thinks adaptively
  even at low effort, and thinking counts toward the limit. Reply length is held
  by the prompt (about 100 words) and cost by the monthly cap. The tutor runs at
  `effort: low` and sends no `temperature`, which Sonnet 5.5 rejects.
- **No server-side refusal fallback.** The API's `fallbacks` option only retries
  `cyber` and `frontier_llm` declines, which a math tutor won't hit. A refusal
  shows the worked solution, like any other tutor failure.
- **Extra columns.**
  - `sessions` holds the problem in progress and the feedback being shown
    (`target_count`, `picked_count`, `phase`, `current_json`, `feedback_json`,
    `retry_pending`), so reloads and double submits can't skip or repeat
    anything, and answers never reach the browser early.
  - `tutor_conversations` keeps `api_messages_json`, the exact messages sent to
    the API, because thinking and tool blocks must be passed back unchanged.
- **`1:50` is read as 50**, so målestok answers can be typed the way they're
  written.
- **A tutor conversation only opens while that answer's feedback is on screen.**
  This makes "the tutor never sees the next problem" hold even for an old tab.
